# 缓存不命中修复：会话粘性 + 缓存用量透传

本版处理下游反馈的「没有缓存」。查下来根因不在缓存开关，而在两处：同一段对话
的每一轮落到了不同的号上，以及缓存用量从来没有被读出来过。

## 修复

### 并发时同一段对话会跳到别的号

「这段对话优先用上次那个号」的提示原本存在号池的全局字段上。号池是进程内单例，
两个同时进行的请求会互相覆盖：A 请求设的号被 B 请求改掉，A 结束时又会把 B 的清空。

结果是并发一上来，粘性基本失效——同一段对话的请求在多个号之间来回跳。

现在这个提示随每次选号单独传递，不再共享。单进程高并发下也稳定。

### 客户端不发会话键时，粘性根本没生效

会话粘性只在客户端主动上报会话标识时才起作用。但主流 SDK 默认都不发这些字段，
于是绝大多数请求走的是「每轮重新按负载均衡选号」。

上游的前缀缓存是**按账号隔离**的：换号就等于缓存全部未命中。所以这不是优化项，
而是命中率的第一决定因素。

- 新增识别 `prompt_cache_key`。这是 OpenAI SDK 的官方缓存路由字段，客户端用它
  表达「这几轮是同一段对话」，本地拿它当会话键正是它本来的意思。
- 新增「无会话键时按首条消息兜底」，**默认开启**：客户端一个键都不发时，
  用首条用户消息派生一个绑定键，让多轮对话稳定落在同一个号上。
- 代价是首条消息相同的不同对话会被当成同一段。介意的话可在
  「设置 → 调度 → 无会话键时按首条消息兜底」关掉，行为回到旧版。

### 缓存用量现在会透给下游

此前三条协议的 usage 里都只有输入/输出/总量，缓存相关字段整体被丢弃。
Anthropic 客户端读的是 `cache_read_input_tokens`，这个字段从来不存在，
所以它永远算不出缓存命中。

- 解析同时认两种方言：OpenAI 的 `prompt_tokens_details.cached_tokens`，
  Anthropic 的 `cache_read_input_tokens` / `cache_creation_input_tokens`。
- 对外按各自协议输出：OpenAI 输出 `prompt_tokens_details`，Anthropic 输出
  `cache_read_input_tokens`（且 `input_tokens` 按 Anthropic 口径剔除缓存部分），
  Responses 输出 `input_tokens_details`。
- **上游没回传缓存字段时，不会输出任何缓存字段**。面板对应位置显示「—」，
  而不是 0%。「不知道」和「没命中」是两件事，后者会误导人以为缓存失效了。
- 缓存命中量落进流水与日聚合，报表新增「缓存命中率」，流水详情能看到单条命中的占比。

> 说明：上游是否回传缓存字段取决于上游实现。若不回传，本节新增的报表指标会显示「—」，
> 但这套透传本身不会产生任何副作用。命中率的实际改善来自上面两项粘性修复。

## 升级说明

- 直接替换二进制或拉新镜像，无需手工操作。
- 数据库给 `usage_logs` 与报表日聚合表补了 `cached_tokens` 列，启动时自动迁移，
  旧库可直接使用；历史流水该列为 0，不影响其它统计。
- 原有环境变量全部兼容。新增一个（只是首次启动的默认值，面板保存后以面板为准）：
  - `SESSION_AFFINITY_FALLBACK`（默认 `true`）：无会话键时按首条用户消息兜底粘性。
- **行为变化**：兜底粘性默认开启后，同一客户端发来的、首条消息相同的多个对话
  会尽量落在同一个号上。这通常正是想要的（并发分散到多个号上会让缓存全部失效），
  但如果你的场景需要每轮重新均衡，请在面板关闭该开关。
